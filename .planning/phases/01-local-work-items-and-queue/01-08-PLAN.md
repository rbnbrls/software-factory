<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local config file → policy | Operator-authored JSON decides which repositories and categories are legal |
| repository key → filesystem/paths | A key is used for lookup and reporting, never as a path segment |
| provider references → workflow state | Opaque annotations must never influence identity or eligibility |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-25 | Tampering | repository key used near path operations | high | mitigate | `^[a-z0-9][a-z0-9-]{0,63}$` with no `/`, no `..`, no uppercase, enforced at load and at use; keys only index a `Map`, never a filesystem path. |
| T-1-26 | Tampering | `providerRefs` content | medium | mitigate | Provider refs are opaque strings stored verbatim; they never affect `isEligible` (which reads only local fields) and a null slot only warns. |
| T-1-27 | Information Disclosure | config secrets | low | mitigate | Phase 1 config contains no credentials by contract; provider slots are `null` and a later phase must keep secrets outside Git (documented in `WORKFLOW.md`). |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No install; config parsing uses `JSON.parse` plus explicit field reads, no schema library. |
</threat_model>
