  <context>
    This is a one-way door: once items exist and approvals are bound to hashes over their content, changing the encoding requires rewriting every item and invalidating every approval (a data migration across the whole factory tree). D-01 already fixes "operator edits Markdown directly"; what is not yet settled by a human record is the machine-readable encoding inside the file.
  </context>
  <options>
    <option id="json-frontmatter">
      <name>JSON object between `---` delimiters + Markdown body sections (recommended)</name>
      <pros>Zero dependencies; no YAML implicit typing (priority 0200 cannot become 128, owner "no" cannot become false); scope and criteria stay readable multi-paragraph Markdown; JSON is a YAML 1.2 subset so a future YAML reader still parses the frontmatter.</pros>
      <cons>Frontmatter is slightly noisier to hand-edit than YAML (quotes and commas); requires a small split/parse module.</cons>
    </option>
    <option id="yaml-frontmatter">
      <name>YAML frontmatter + Markdown body sections</name>
      <pros>Familiar Jekyll/Obsidian convention; friendlier hand-editing of scalars.</pros>
      <cons>Needs a YAML parser dependency or a hand-rolled subset; implicit typing and schema-version differences create silent type drift in the exact fields (priority, owner) that gate the queue.</cons>
    </option>
    <option id="all-json">
      <name>One JSON document (no Markdown body)</name>
      <pros>Single parser; trivially machine-validated.</pros>
      <cons>Multi-paragraph scope and acceptance criteria become escaped `\n` strings — hostile to the operator's direct editing, contradicting D-01.</cons>
    </option>
  </options>
