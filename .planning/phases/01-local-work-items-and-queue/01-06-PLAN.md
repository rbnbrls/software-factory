<objective>
**As the** operator, **I want to** approve an exact revision and have any scope edit automatically invalidate that approval, **so that** no agent can act on a specification I have not seen.

ROADMAP Phase 1 goal (verbatim): "The operator can safely define, approve, prioritize, and resume work from local Markdown."

Purpose: WF-03 and D-03/D-04. Approval is the human-control gate of the whole factory (C5). It must be a hash over the approved specification — robust to formatting noise, sensitive to content — and it must fail closed the moment scope changes.
Output: the full revision contract with its boundary tests, drift detection in `validate`, `factory show`, `factory approve` hardening, and `reconcile` step 4.
</objective>

  <behavior>
    - Test 1 (stability): LF vs CRLF, trailing spaces, trailing tabs, one vs three blank lines between paragraphs, and a leading/trailing blank line all hash identically.
    - Test 2 (sensitivity): one added character in Scope, in Out of Scope, in a criterion, in `repository`, or in `targetBranch` each change the hash.
    - Test 3 (adjacency): a criterion with a single space between words vs two spaces hash identically (internal whitespace collapsed for criteria) but two spaces inside Scope are preserved and hash differently.
    - Test 4 (ordering): criteria `["a","b"]` and `["b","a"]` hash differently; criterion count is in the payload so `["a"]` vs `["a",""]` differ.
    - Test 5 (precision): scope `"x:y"` with criterion `"z"` differs from scope `"x"` with criterion `"y:z"` and from scope `"x"` with criterion `"y"` + `"z"`; a 3-byte UTF-8 character (e.g. `€`) uses its byte length, not its code-unit length.
    - Test 6 (empty): empty Scope, whitespace-only Scope, and `Out of Scope: "None."` each produce a stable, distinct hash; an empty criteria array still hashes deterministically (validation rejects it upstream, the hash function does not throw).
    - Test 7 (format): every result matches `/^sha256:[0-9a-f]{64}$/`; `REVISION_FORMAT` is part of the payload (assert by hashing with a bumped constant in a local copy and requiring a different digest).
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator edit → approval validity | File content decides whether a prior human decision still applies |
| approval record → queue eligibility | A hash match is the only admissible proof |
| decisions log → audit | Append-only history that must survive invalidation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-19 | Repudiation | approval reused for changed content | high | mitigate | `approval.revision` is recomputed on every load and compared; mismatch excludes/marks the item; there is no stored `approved: true`; `approve` refuses a caller-supplied revision; `REVISION_FORMAT` is payload-bound. |
| T-1-20 | Tampering | approvals log rewrite | medium | mitigate | Append-only via `O_APPEND` + `flush:true`; torn last line ignored with a warning; no code path rewrites or truncates the log. |
| T-1-21 | Information Disclosure | approval summary printed to stdout | low | mitigate | Summary and prompt go to stderr; stdout stays machine output only, so a pipeline never captures or re-parses the human text. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No install; hashing uses `node:crypto` only. |
</threat_model>
